# **1\. Task 1 – Prototype**

## **1.1 Overview**

Our prototype, [scraper.py](https://github.com/wenkow2k515/CITS5501-3501-Group-Project/blob/main/scraper.py), is a Python script built on the supplied starter code. It uses the `requests` library for HTTP and BeautifulSoup to parse HTML. By default it starts from the [policy index page](https://uwa-policy.cits5501.arranstewart.io/policy/); an alternative start URL can be given as a command-line argument, so the same script can be run against a local copy of the site during testing.

The scraper works in four stages:

1. **Fetch the index page.** The HTTP status and declared content type are printed.  
2. **Extract links.** Every `<a href>` element is collected and resolved to an absolute URL against the final URL of the index response.  
3. **Select policy documents.** A link is treated as a policy document if its path ends in a document extension (`.pdf`, `.doc`, `.docx`, `.xls`, `.xlsx`, `.ppt`, `.pptx`, `.rtf` or `.odt`). The check is case-insensitive and ignores query strings. Links to other hosts are excluded, and URL fragments are removed before duplicate URLs are discarded. Different URLs may still refer to identical document contents.  
4. **Download and report.**The scraper attempts to download the first three distinct document URLs. For each, the scraper prints the URL, HTTP status, declared `Content-Type`, downloaded size in bytes and the first 10 bytes of the body, so the `%PDF` or `PK` file signature can be checked. The downloaded data is then discarded.

All requests go through the starter's `fetch()` function, which enforces a 10-second timeout, waits 1 second between fetch calls, and a limit of 20 fetch calls per run. Automatic redirect requests are not counted separately, therefore a typical run without redirects makes four HTTP requests consisting of the index page and 3 documents

## **1.2 Limitations**

Because the prototype is intentionally minimal, it has several limitations:

* **Success is judged by status code only.** Any `200 OK` response is reported as a successful download, so a `.pdf` link that returns an HTML page, or a corrupt PDF, would still be reported as successful. The first bytes are printed but not checked against the expected file type; the artefact in section 3.4 demonstrates this failure.  
* **Documents are identified by file extension only.** Documents served from URLs without an extension (for example `/download?id=12`) are missed, and any URL ending in a document extension is assumed to be a document.  
* **Network errors are not handled.** A timeout or connection error raises an unhandled exception and ends the run, rather than being reported for that document while the remaining downloads continue. The brief does not require this for the prototype, but a production scraper would need it (see tests T005 and T006).  
* **Only static links are found.** Links generated by JavaScript or held in markup other than `<a href>` are not discovered, and the scraper cannot distinguish an index page with no documents from one whose structure has changed.  
* **Responses are read fully into memory.** Each response is read in one go rather than streamed, so a very large file could exhaust the available memory.

## **1.3 Assumptions**

To keep the prototype within the scope of the brief, we made the following assumptions:

* All policy documents are linked directly from the index page, so no recursive crawling is needed, as permitted by the brief.  
* Policy documents are served from the same host as the index page, so links to other hosts can be ignored.  
* Downloading three distinct documents is enough to demonstrate the approach, and stays well within the 20-request limit.  
* Relative links are resolved against the final URL of the index response, after any redirects.

# **2\. Task 2 – Design of test suite**

A production scraper targets one known site, so in most of these scenarios it cannot recover by itself. The reasonable expectation is that it fails predictably and visibly. Across all scenarios, a well-engineered scraper should:

* never terminate with an unhandled exception;  
* never report a failed or invalid download as successful;  
* report what went wrong, and for which URL;  
* continue with the remaining documents where it is safe to do so;  
* stay within its request limit, including any retries.

## **2.1 Expected behaviour per scenario**

1. **Website structure changes.** If policy links are still ordinary `<a href>` elements, they should still be found. If the page loads but no policy links are found, the scraper should report a probable structure change and exit with an error, rather than finishing successfully with no results.  
2. **Truncated HTML.** The scraper should not crash. Complete links should still be processed and a partial link should not be requested. A warning should be required when there is evidence of an interrupted transfer, such as fewer bytes arriving than the declared content length. A missing closing \</html\> tag alone does not establish truncation  
3. **Timeouts (short or long).** Every request needs a timeout. If the index page times out, nothing further can be done, so the scraper should report this and stop. If a single document times out, it should be reported as failed and the scraper should move on. A short outage may justify a limited retry, provided retries count towards the request limit.  
4. **4xx and 5xx responses.** The status code should be checked before the response body is used. An error page returned for the index must not be parsed as the index, and an error response for a document must never be counted as a downloaded document.  
5. **Malformed Office or PDF files.** The file extension should not be trusted. The declared `Content-Type` and the file signature (`%PDF` for PDF, `PK` for Office Open XML formats such as `.docx`) should be compared with what was expected, and a mismatched or unreadable file reported as a failure.

# **3\. Task 3 – Fixtures and test doubles**

## **3.1 Fixtures as a source of truth**

Each test compares the scraper's output with a fixture whose correct result is known in advance. We would use:

* **Saved HTML pages.** A copy of the policy index page captured once from the live site and stored in the repository, plus variants derived from it: restructured markup, a truncated copy and a copy with the links removed (T002 to T004). For each page we record the exact list of document URLs that should be found.  
* **Sample policy files.** Known-good PDF and DOCX files, and deliberately broken ones: an HTML page saved under a `.pdf` name and a PDF cut off after its header (T009, T010). Each file is stored with its expected status, content type, size and signature.  
* **A local HTTP server.** A small server, started by the tests, that serves these pages and files from `localhost` and can be configured to return chosen status codes, headers or delays (T005 to T008).

Because the fixtures only change when we change them, a failing test points to the scraper rather than to the site. The captured index page should still be refreshed occasionally and compared with the live site by hand, so the fixtures stay representative.

## **3.2 Request limits on the target site**

We probed the site with curl from one machine, identifying the requests with our scraper's User-Agent name. A `HEAD` request for one policy PDF returned `200 OK` with `Content-Type: application/pdf` and a `Content-Length` of 163,909 bytes, together with the headers `X-Ratelimit-Limit: 3`, `X-Ratelimit-Remaining: 2`, `X-Ratelimit-Reset` and `Retry-After: 10`. The site is served through Cloudflare.

We then downloaded the same PDF ten times in a row with no delay between requests (each took about 0.4 seconds). The first six requests returned `200 OK` with the full 163,909 bytes. Requests seven to ten returned `429 Too Many Requests` with a 40,740-byte error page instead of the document.

The site therefore does limit requests. The headers advertise a limit of three, yet six back-to-back downloads succeeded before the first 429, so the exact limit and window are not stated; we did not probe further, to stay within the brief's limit of ten downloads. This affects testing in two ways: a scraper has to space its requests and honour `Retry-After`, and a 429 response must never be counted as a downloaded document, even though its size looks plausible.

Because the live site limits requests, the Task 2 tests should not run against it at all. They run against the fixtures and test doubles described in 3.1 and 3.3, which allows any number of runs, including in CI. The live site is then used only for an occasional smoke test that stays well within its limit, and to refresh the captured fixtures.

## **3.3 Simulating network failures with test doubles**

Test doubles can simulate timeouts, interrupted downloads, connection failures and very slow responses without touching the live site. In Python this can be done at three levels:

* **Replacing the HTTP call.** `unittest.mock.patch` or pytest's `monkeypatch` can replace `fetch()` or `requests.Session.get` with a double that raises `requests.exceptions.Timeout`, `ConnectionError` or `ChunkedEncodingError` (an interrupted download). The `responses` and `requests-mock` libraries do the same per URL, returning chosen status codes, headers and bodies. These doubles are fast and deterministic: a timeout test raises the exception immediately instead of waiting for the real 10-second limit.  
* **A real local server.** `pytest-httpserver`, or Python's built-in `http.server` running in a thread, can delay a response beyond the client timeout, send data a few bytes at a time, or close the connection part-way through a body whose `Content-Length` promises more. These cases depend on real socket behaviour, so a mock of `requests` cannot reproduce them faithfully.  
* **Network-level faults.** Toxiproxy runs between the scraper and a server and adds latency, bandwidth limits or connection resets, which suits tests of very slow or unstable connections.

## **3.4 Demonstration artefact**

Our artefact, [fixtures/fake\_pdf\_server.py](https://github.com/wenkow2k515/CITS5501-3501-Group-Project/blob/main/fixtures/fake_pdf_server.py), demonstrates Task 2 scenario 5 (tests T009 and T010). It is a local server, written with only the Python standard library, that serves a policy index linking to three documents:

* `valid.pdf`: a minimal well-formed PDF served as `application/pdf`;  
* `not-a-pdf.pdf`: an HTML error page served with `200 OK` and `Content-Type: text/html`;  
* `corrupt.pdf`: a 40-byte file that starts with `%PDF` but is truncated, with no `%%EOF` marker.

Run against this server, the Task 1 prototype reports all three documents as "Downloaded successfully", although the second is an HTML page and the third cannot be opened by a PDF viewer. [tests/test\_fake\_pdf.py](https://github.com/wenkow2k515/CITS5501-3501-Group-Project/blob/main/tests/test_fake_pdf.py) automates the check: the valid-PDF test passes and the other two fail, which is the failure the fixture was built to expose. Both files are in the submitted zip, and README.md explains how to run them.

The same scenario is difficult and undesirable to reproduce against the live site:

* we do not control the live server, so we cannot make it return HTML or a corrupt file for a PDF link on demand;  
* even if a broken document existed there, it could be fixed or removed at any time, so the test would not be repeatable and its expected result would not be known in advance;  
* every run would use requests on a shared, rate-limited site, and would fail whenever the site or network was unavailable, for reasons unrelated to the scraper.
